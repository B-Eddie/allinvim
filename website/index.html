How it works

Three Vims. One router. Zero fights.

General Vim layers the Vim-For-Textarea direct executor and the Vim-For-Docs synthetic executor inside Vimium navigation. A single capture-phase listener decides the owner per keystroke — editor keys never leak into page scroll, and page keys never type into your buffer.

Questions

FAQ

Which sites does it work on?

Every site. Page navigation runs on all URLs; text editing activates in any textarea, text input, contenteditable, Google Docs document, or supported code editor.

How does the handoff avoid conflicts?

One capture-phase router runs before Vimium. Editing keys are consumed with stopImmediatePropagation so navigation never sees them; otherwise the router stays silent and Vimium navigates. Visible Vimium overlays always win, except the commit/discard overlay which owns the keyboard.

Why an overlay for code editors?

Framework editors own their document model — in-place key surgery desyncs it. Editing in our own exact textarea and committing once (the Surfingkeys/wasavi pattern) is the only correct approach.

Is it fast on heavy pages?

Yes. document_start injection, inlined config (no fetch, CSP-safe), targeted hint selectors, rAF-coalesced caret, and memoized context checks. No polling.

Can I remap keys or exclude sites?

Yes. Vimium custom key mappings, the shared motions JSON, and per-pattern exclusion rules in Options.
